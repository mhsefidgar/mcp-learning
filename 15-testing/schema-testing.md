# Schema Testing

## What is it?

**Schema testing** pins the exact JSON Schema a server advertises for its tools
(and prompt arguments). It is contract testing for the *shape* of requests.

## Why does MCP need it?

A tool's schema is what the agent uses to build arguments. If the schema drifts
from the implementation — a `required` field added, a parameter renamed, a type
loosened — agents either fail to call the tool or call it wrong, in ways that
only show up in production. Pinning the schema makes drift a failing test.

## How it works

1. Fetch the advertised schema: `tools/list` returns each tool's
   `inputSchema`.
2. Assert on the parts that matter: property names, types, `required`,
   descriptions, defaults, enums.
3. Assert the schema *validates* what the tool accepts: run sample valid and
   invalid arguments through a JSON Schema validator (or simply through
   `call_tool`) and confirm the boundary.

## Example

```python
import json
from fastmcp import Client

async def test_schema_contract():
    async with Client("server.py") as client:
        tools = await client.list_tools()
        schema = next(t.inputSchema for t in tools if t.name == "add")

        assert schema["type"] == "object"
        assert set(schema.get("required", [])) == {"a", "b"}
        assert schema["properties"]["a"]["type"] == "integer"
        assert schema["properties"]["b"]["type"] == "integer"
        # no defaults carrying secrets, no undocumented extra params:
        assert "password" not in json.dumps(schema)
```

## MCP-specific behavior

- The schema is generated by the SDK from your function signature/types
  (FastMCP uses pydantic) ([04-tool-engineering/schemas.md](../04-tool-engineering/schemas.md)).
  Test the *advertised* schema — that is what clients see — not your source.
- FastMCP's `@mcp.tool` with a `Context` param injects it internally; the
  advertised schema should NOT include framework-injected params.

## Industry-standard pattern

**Schema snapshots / contract tests** run in CI against every change: a diff of
the advertised schemas is reviewed like an API diff, because that is what it is.

## Common mistakes

- Testing only that a schema *exists* (non-empty) — drift passes silently.
- Asserting on serialization order or ref mechanics instead of semantics.
- Missing the security angle: defaults or descriptions can leak secrets or
  internal details ([14-security/sensitive-data-redaction.md](../14-security/sensitive-data-redaction.md)).
